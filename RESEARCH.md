# Research

Notes and findings that don't belong in TODO.md or README.md.

## iDRAC virtual console options
- iDRAC VNC server: TCP 5901, off by default, 8-char password. Enable via UI (Configuration > Virtual Console) or `racadm set iDRAC.VNCServer.Enable Enabled`. Untested.
- Rust `vnc` crate 0.4.x implements an RFB client; auth/encoding support against iDRAC unverified.
- iDRAC9 firmware >= 6.00.02.00: console is eHTML5 over 443 only; no public protocol spec or Rust implementation found.

## VNC on iDRAC (verified 0.0.9)
- iDRAC VNC identifies as "OpenVNC", 1024x768; `vnc` 0.4 crate handshake with VNC password auth works; incremental updates arrive (small repeated rect at 192,766 32x2).
- iDRAC seems to allow a single VNC client; a second concurrent connection fails the handshake ("failed to fill whole buffer").
- Headless (Xvfb) screenshots of the Tauri window came out black, so rendering was not confirmed that way.

## iDRAC VNC encryption (probing 0.2.4)
- `racadm set iDRAC.VNCServer.SSLEncryptionBitLength` only accepts numbers: 0 Disabled, 1 Auto Negotiate, 2 128-Bit or higher, 3 168-Bit or higher. Names are rejected (RAC947). racadm over SSH exits 0 on errors; check output for "ERROR". `;` can't chain commands.
- RESOLVED: with encryption on (Auto Negotiate), port 5901 speaks TLS from the first byte (stunnel-style), TLS 1.2, cipher AES256-GCM-SHA384 (static RSA key exchange, so rustls can't be used; `openssl` crate needed), self-signed Dell cert, and the server takes ~10-12s to answer the ClientHello (earlier probes timed out at 8-10s and wrongly saw silence). After the handshake the normal `RFB 003.008` greeting follows. Python needs `ALL:@SECLEVEL=0` to negotiate it.
- SSVNC (SSL mode) connected then exited right after the handshake in the packet capture; cause not investigated.
- iDRAC8 firmware 2.86.86.86, BIOS 2.19.0.

## Encodings (0.4.0)
- iDRAC8 VNC native pixel format: 16bpp, depth 15, RGB555, little endian. Supports Zrle (full 1024x768 as 64x64 tiles in ~0.3s over TLS vs ~2.3s Raw 32bpp).
- `vnc` 0.4 crate decodes only Raw, CopyRect, Zrle, Cursor, DesktopSize (Hextile/RRE return an error). `Client::set_format` hangs when updates arrive as tiles (it waits for one full-screen rect), so switch format first (while still on Raw), then enable Zrle. Using the server's advertised native 16-bit format produced wrong colours (light blue/cyan), so force 32-bit BGRX instead.

## HTML5 console (0.8.0)
- iDRAC8: `iDRAC.VirtualConsole.PluginType` 2 = HTML5 (the names `HTML5` and `Java` are also accepted: Java reads back as 1, HTML5 as 2; 0 is ActiveX). `iDRAC.VirtualConsole.Enable` must be Enabled. Console port 5900, Timeout 1800, MaxSessions 6.

## Serial over LAN (0.9.1)
- iDRAC8 attributes: `iDRAC.IPMILan.Enable`, `iDRAC.IPMISOL.{Enable,BaudRate,MinPrivilege}` (MinPrivilege 4 = Administrator), `iDRAC.Serial.Enable`, `iDRAC.SerialRedirection.Enable`; BIOS `BIOS.SerialCommSettings.{SerialComm,SerialPortAddress,RedirAfterBoot,FailSafeBaud,ConTermType}`. Test server already had SerialComm=OnConRedirCom2, SerialPortAddress=Serial1Com2Serial2Com1, RedirAfterBoot=Enabled, FailSafeBaud=115200, ConTermType=Ansi, IPMISOL baud 115200, iDRAC.Serial baud 57600.
- BIOS attribute changes are staged and need `racadm jobqueue create BIOS.Setup.1-1` plus a reboot to apply.

- `ssh <user>@idrac console com2` (PTY + exec `console com2`) prints "Connected to Serial Device 2. To end type: ^\" (quit key set by iDRAC.SerialRedirection.QuitKey). It coexisted with an active ipmitool SOL session. SOL via `ipmitool -I lanplus` works with the default cipher suite (17) on iDRAC8 2.86.86.86.

## Serial console redraw scrolling (0.9.9)
- The TrueNAS console menu (prompt_toolkit) asks the cursor row with ESC[6n, then prints (H - row) newlines and moves up that many lines, where H = 66 is the height the remote tty believes (independent of our pty size: tested with 30, 50 and 70 rows). With a reported row of 66 or more it prints none and redraws in place. A terminal shorter than 66 rows therefore scrolls on each redraw; a tall terminal (as in the CLI) does not. Reproduced with a pty harness that answers ESC[6n with a chosen row (14 -> 52 newlines, 40 -> 26, >=66 -> none).
- The remote also double-translates newlines (`\r\r\n`), which is harmless.

## Screen to text (1.0.5)
- iDRAC8 VNC shows the Linux console as 1024x768 with an 8x16 bitmap font (128x48 cells, 3 colours, no anti-aliasing), so every character is one of ~50 repeated shapes.
- Cell size detection: for each candidate size count distinct non-empty cell shapes; the true size gives a tiny ratio (47 shapes / 1941 cells = 0.024). Divisors of the true size (8x8, 4x8) also score well, so pick the LARGEST candidate with ratio <= 0.08.
- Whole-screen OCR with word boxes mis-aligned columns (drwxr-xr-x came out as drrxr-xr-x). What works: stack only the non-empty rows with a full row of white between them (one row = one OCR line), accept a line only if tesseract returned exactly as many characters as there are non-blank cells in that row, vote per shape across lines and several scales, then assign characters to shapes one-to-one by descending votes (a real `8` has its own shape and wins the 8, leaving the 0 shape its 0).
- Image scaling matters: nearest-neighbour upscaling halves the accepted lines and reads 0 as @; bilinear (3x, 4x, 5x) matches Lanczos. A gap of half a row between rows confused 0/@ again; a full row gap fixed it. tesseract accepts a plain binary PGM on stdin.
- A render taken mid-scroll leaves fragments of the old text; after the picture settles (250ms) ask for one full non-incremental update and render that.
- Calibration takes ~5s (3 tesseract runs in parallel); shapes a calibration could not name (a glyph clipped at the screen edge) are given up on so they don't trigger more runs.
- The iDRAC sends no RFB greeting to a plain client when VNC encryption is on, so `--notls` would hang without a read timeout.
- Digit confusion (1.0.7): on the 8x16 Linux console font tesseract reads the `0` shape as 6 (62 votes), @ (27), 8 (25) and 0 (20); the real `6` and `8` shapes claim their own characters first, so the zero shape gets whatever is left, and by raw votes that was `@` on one screen and `0` on another. Scoring each (shape, character) as share-of-the-shape's-votes x a rough character-frequency prior (@ rare, 0 common) picks 0 on both and leaves @ for the prompt's shape.

## iDRAC8 HTML5 console (1.1.0 - 1.1.1)
- The iDRAC web server serves static pages and files (start.html, login.html, js/...) only to clients that send `Accept-Encoding: gzip`; otherwise 404. Data endpoints (`/data/login`, `/session?...`) work without gzip.
- Login: `POST /data/login` with `user=...&password=...` (urlencoded) returns XML with `authResult` (0 ok, 1 wrong password, 5 no free session) and `forwardUrl` = `index.html?ST1=<t1>,ST2=<t2>`, plus the `-http-session-` cookie (secure, httponly). Login takes ~5s; other requests are fast. `/session?...` calls need the header `ST2: <t2>`. `/data/logout` ends the session (303).
- Console URL (from LaunchConsole.jsesp): `https://<ip>/virtualconsolehtml5.html?ipAddr=<ip>&kvmPort=<rp_int_apcp_port, 5900>&vmPriv=<true|false>&lang=en&aimSession=<getSsnVar aimSession>&ST2=<t2>&TokenName=ST1&TokenKey=<t1>`. Requires `gui_kvm_plugin_type` = 2 (HTML5), `vkvm_bool_enabled` = 1 and `accessConsoleRedirection` = 1.
- The viewer page (virtualconsolehtml5.html) reads `window.opener.top.localeObj` (the language JSON `/locale/locale_en.json`, whose inner `localeString` object is what the web UI assigns to `localeObj`) and sets `window.opener.top.htmlViewerWindow = null`, so it only works as a pop-up of the web UI unless an `opener` is injected before its scripts run. With the stand-in opener the page opens two WebSocket connections to port 443 (about 15 KB and 5.5 KB received for a static screen).
- The web certificate on 443 is the same certificate as on the VNC port 5901, so one pin covers both.
- Headless WebKit (Xvfb, no window manager or GPU) paints nothing, so the console cannot be seen in automated tests; connections and logout were checked on the iDRAC side (`racadm getssninfo`).
- The viewer's first step (rpviewer.js `RP_API_ERROR.POPUP_BLOCKED`) is a certificate dialog: `window.open("https://<ip>:<kvmPort>/<page>", canvasId, "width=700,height=500,...")`, then every 250 ms `popup.postMessage("Hello","*")`; when a `message` event arrives whose origin equals `https://<ip>:<kvmPort>` it proceeds to open its WebSockets. If `window.open` returns null it reports POPUP_BLOCKED ("Turn off your pop-up blocker and try again!"). Port 5900 serves HTTPS ("WS server test page") with the same certificate as 443. The window must therefore be allowed and keep its `opener`.
- WebKitGTK blocks `window.open()` that is not user-initiated by default (`javascript-can-open-windows-automatically` is false) and returns null without emitting the `create` signal, so the app's `on_new_window` handler is never called; the viewer opens its certificate window from its load script, so the setting must be enabled for the console window.
- Killing the console window without running the viewer's `disconnectKVM()` (which calls `exitViewer()` and sends the close-connection messages on the primary and video sockets) leaves the iDRAC's "Virtual Console" session (racadm getssninfo) listed for at least a minute after the sockets are gone. The page's Disconnect Viewer button calls `disconnectVM(); disconnectKVM();`.

## Embedding the HTML5 console (1.1.7)
- Tauri 2 can host a second web view in a window (`Window::add_child`, `unstable` feature). On Linux (`build_gtk` into the window's `default_vbox`) the child is packed into the vertical box and its position is ignored; positioning only works under a `gtk::Fixed` parent. So layout is done in GTK: the child expands, the main page is wrapped in a fixed-height `gtk::EventBox` at the top.
- A size request on the main WebKitWebView is only a minimum: its natural height stays "the whole window" (preferred height min 112, natural 800), so with expand=false it still took 800px and left the console 1px. Wrapping it in an EventBox with `set_size_request(-1, h)` works (EventBox preferred height = the request).
- GTK allocates widget sizes even on Xvfb, so layout can be verified headless by logging `allocation()`; painting cannot.

## Controlling the embedded HTML5 console from outside (1.1.9)
- Dell's viewer registers `keydown`, `keypress` and `keyup` listeners on `window` (and `blur`, `visibilitychange`); it maps `event.keyCode` / `event.code` to USB keys. Dispatching `new KeyboardEvent(...)` on `window` with `keyCode`/`which` defined on the event types text into the console (a Shift keydown/keyup around shifted characters, 12ms between characters). Verified on the TrueNAS console.
- The page loads Prototype.js, which changes `Array.prototype`: `Array.prototype.map.call(HTMLCollection, ...)` fails ("this.each is not a function") and `JSON.stringify([...])` is double-encoded (a quoted string). Use `forEach` loops and `join(',')`.
- `webview.set_zoom(f)` zooms the whole page (Dell's buttons too); the canvas then overflows and scrolls.
- `WebViewExt::snapshot(SnapshotRegion::Visible, ...)` returns a cairo surface even on Xvfb, so a headless test can see the console; WebViewExt::run_javascript (deprecated since WebKit 2.40) returns a script's value. Commands that wait for these must not run on the main thread (use `async` commands).
- tesseract on the console canvas: bilinear 4x of the inverted grayscale reads `<user>@<host>[/]# a` exactly; cairo's own 3x scaling read `[/]#` as `(7)`; Lanczos 3x added a space.

## Java console (1.3.6; iDRAC8 firmware 2.86.06, macOS on Apple Silicon)
- `iDRAC.VirtualConsole.PluginType` 1 makes `gui_kvm_plugin_type` read 1; the login checks (`/session?aimGetIntProp=...`) are the same as for HTML5.
- After the normal web login, `GET /viewer.jnlp(<ip>@0@<title>@<unix ms>@ST1=<token>)` (with the session cookie and ST2 header) returns the Web Start file (`application/x-java-jnlp-file`). Its `<argument>` list is what the viewer takes: `ip`, `vm`, `title`, `user=<n>@@<n>` and `passwd=<n>` (one-time values the iDRAC creates for that request, not the login password), `kmport`/`vport` 5900, `apcp=1`, `reconnect`, `chat`, `F1`, `custom`, `scaling`, `minwinheight/width`, `videoborder`, `version=2`. Main class `com.avocent.idrac.kvm.Main`, jar `/software/avctKVM.jar` (1.4 MB), native libraries per OS/arch as `nativelib` jars (`avctKVMIOMac64.jar`, `avctVMAPI_DLLMac64.jar` for `Mac OS X`/`x86_64`; Linux/Windows have their own).
- The jars can be run without Web Start: `java -Djava.library.path=<dir with the unpacked natives> -cp avctKVM.jar com.avocent.idrac.kvm.Main <arguments>`. Dell's Mac natives (`.jnilib`) are x86_64 only, so on Apple Silicon an x86_64 Java under Rosetta is needed (Azul Zulu 8 JRE macosx_x64 works).
- On macOS the viewer was killed right after the TLS handshake with "java is loading libcrypto in an unsafe way": `libVMAPI_DLL.jnilib` calls `dlopen("/usr/lib/libssl.dylib")` and is written to fall back to its built-in OpenSSL if that fails, but Apple's stub library aborts the process instead. Not fixed by an empty `libssl.dylib` in `java.library.path` or by `DYLD_LIBRARY_PATH` (the dlopen uses the absolute path); `vm=0` does not avoid it. Replacing the string with a same-length path that does not exist (`/usr/lib/libssl.dyl_x`) in the downloaded copy makes the load fail normally and the viewer continues. `lldb` cannot attach to the Rosetta process here.
- After that the iDRAC closed the console connection (port 5900) during the TLS handshake ("Exception in server handshake ... readHandshakeRecord", broken pipe after the client's Finished). With `-Djdk.tls.client.protocols=TLSv1.2 -Djdk.tls.useExtendedMasterSecret=false` the session runs ("login succeeds", "KVM session is running", "Video connect status: true", resolution reported). The two flags were only tested together; single-flag runs were disturbed by leftover sessions.
- The viewer's certificate warning ("The connection to <ip> is untrusted ... unable to get local issuer certificate", buttons Details/Run/Cancel) comes from its own OpenSSL check of the console certificate (`OpenSSLTrustManager` -> `X509CertificateJNI.ValidateX509Certificate` in `libavctKVMIO.jnilib`, a statically linked OpenSSL). It only offers "always trust" for self-signed certificates ("Certificate is not a self signed type" is logged first). Preferences (`java.util.prefs`, `~/Library/Preferences/com.avocent.viewer.plist`, key `USER_CERT_STORE_PATH`) hold its settings. `SSL_CERT_DIR` does not help (tried: the reason stayed "self signed certificate" for a default Dell certificate in a directory that held it). The dialog for an untrusted certificate says "To permanently accept this certificate, specify user's certificate store path in Tools->Session Options->Certificate"; with a store path set it offers "Always trust this certificate" (strings in `com/avocent/client/res/Res_en.properties`: `certificate_Always_Trust`, `Cert_security_user_path`, `CERT_USER_PATH_*`). The path is `USER_CERT_STORE_PATH` under `/com/avocent/viewer/dell/` in the Java preferences, which on macOS is `~/Library/Preferences/com.avocent.viewer.plist` (edit it with `defaults export/import` and PlistBuddy, not by writing the file, because of cfprefsd). It is read when a session starts.
- The viewer warns that its keyboard/mouse native library failed to load (macOS wants Accessibility access for "assistive devices"); typed text still goes through.
- Ending the viewer by SIGTERM/SIGKILL does not run its disconnect: the iDRAC kept the console sessions and later connections were refused until they were cleared with `racadm closessn -a` (over SSH). Closing the viewer's own window ends the session cleanly (`SESSION_CLOSED`, exit status 0). `racadm getssninfo` lists the sessions.
- What "Always trust this certificate" saves: a PEM file in the store folder named `EMR_<SHA-256 of the issuer name in OpenSSL one-line form (`openssl x509 -nameopt compat`, `/C=US/ST=Texas/...`), upper-case hex>_<serial, upper-case hex>.pem`. Writing that file ourselves (as bobcat does from the pinned certificate) is enough; the dialog is skipped.
- macOS Local Network privacy (Sequoia and later): a bundled app that connects to a LAN address without the permission fails with "No route to host" (os error 65) even though ping works. `cargo run` works because it runs under Terminal's permission. Needed for the .app: `NSLocalNetworkUsageDescription` in Info.plist (`gui/src-tauri/Info.plist`, merged by Tauri) and a bundle signature that seals the Info.plist with a stable identifier (`bundle.macOS.signingIdentity: "-"`; a bare ad-hoc signature on the binary has a per-build identifier and does not bind the Info.plist). Confirmed fixed with both in place after reinstalling from the new DMG. The permission cannot be reset with `tccutil`; it lives in System Settings > Privacy & Security > Local Network.
- Java viewer keyboard warning ("Native library for keyboard and mouse support failed to load"): granting Bobcat the Accessibility permission (System Settings > Privacy & Security > Accessibility) stops the popup. The permission does not give clipboard paste in the viewer window, which has none; bobcat's own Paste would need to inject key events from inside the viewer's JVM (a `-javaagent` helper) or from outside through the Accessibility API.
- Driving the Java viewer through the macOS Accessibility API (AXUIElement; needs the permission): its menu bar is fully visible (`AXMenuBar` of the application element: File, View, ...; items have `AXTitle`, press with `AXPress`). View = Refresh, Fit, Full Screen, Session User List; Tools = Single Cursor, Session Options, Stats, Performance, Start Instant Messaging. There is no scaling toggle: "Video Scaling" (`MainMenu_View_Fit_On_Resize`) is not in the menu. Session Options opens as a window titled "Session Options" with an `AXTabGroup` (3 tabs, no attributes, not pressable; the visible General page has "Pass all keystrokes to target."), OK/Cancel/Apply buttons. The window title of the console is `<user>: <name>, <fps> fps` (it does not contain the iDRAC address). The viewer scales the server picture to its window (about 0.69x for a 1600-px server in an 1100-pt window); the Scaling page in Session Options is only aspect-ratio settings (`IDFF_SESSOPTS_MAINTAIN_ASPECT`, windowed and full screen).
- OCR of the viewer screen (Copy): tesseract 5.5 reads about 78% of characters right on a captured, downscaled VGA font. Black-and-white thresholding made it much worse (60% or less); keeping the grays and enlarging 3x with bicubic smoothing was best; resampling back to the font's native size gained only a few points more.
- Glyph matcher prototype for Java Copy (Python, on a saved 2200x1204 capture of an `ls -l` screen, text compared with the real text; not ported): the character grid can be found (pitch from the row/column ink profiles with a multi-lag autocorrelation fit: 10.88 x 21.71 px, a 1:2 cell; the phase is better fitted by minimising the variance of cells of equal characters than from ink minima at the cell borders). Cells resampled to 8x16 with a 1-pixel margin and compared with a small-shift-tolerant RMS distance. Findings: (1) the viewer's picture is compressed, scaled video, so cells of the same character differ a lot: greedy clustering gives 135 clusters for 41 characters even at a strict threshold, and loose thresholds merge different characters; (2) with the true names known, nearest-class-mean classification is 94% right (leave one out; errors i/1, n/r, d/o); (3) names obtained from tesseract (character boxes via `makebox`, one vote per cell, then majority vote among the cells within distance 0.08) give 88% per cell, against 83% for tesseract alone, so the gain is capped by tesseract's own naming errors; (4) tesseract line by line (psm 7/13, scales 2-4) is no better than the whole screen (up to 80%). Conclusion: not worth the port for about 5 points; exact text needs the real framebuffer (the iDRAC VNC console, `bobcat-cli --console vnc`) or a bigger window / smaller server resolution.

## Intel AMT 14.1.79 KVM settings (1.6.x)
- WS-Management on 16992 with HTTP digest (realm `Digest:<hash>`, qop=auth) works; Get of AMT_GeneralSettings, AMT_SetupAndConfigurationService, CIM_AssociatedPowerManagementService, AMT_RedirectionService, IPS_KVMRedirectionSettingData, CIM_KVMRedirectionSAP, AMT_BootCapabilities, AMT_BootSettingData, AMT_TimeSynchronizationService, CIM_PowerManagementCapabilities, IPS_OptInService all answer 200; AMT_EthernetPortSettings, CIM_ComputerSystem and AMT_TLSSettingData need selectors or Enumerate (400 InvalidSelectors). Ports: 16992 (HTTP), 16994 (redirection), 623 open; 16993/16995 (TLS) and 5900 closed.
- The device was provisioned (ProvisioningState 2), OptInRequired 0, KVM SAP EnabledState 6 (enabled, offline), IPS_KVMRedirectionSettingData: Is5900PortEnabled false, EnabledByMEBx true, OptInPolicy false, SessionTimeout 3.
- `CIM_KVMRedirectionSAP.RequestStateChange(2)` returns 0.
- Put of IPS_KVMRedirectionSettingData: AMT's schema wants the instance with at least ElementName, InstanceID, OptInPolicy and RFBPassword (smaller sets: SchemaValidationError); an unchanged Put is accepted; any change to RFBPassword or Is5900PortEnabled (alone, with or without the capability flags) answers `e:UnsupportedFeature`. So on this firmware and configuration the legacy VNC port and password cannot be set through this Put (the reason is still open: another setting that gates it, or the feature is not available on this platform).
- Second diagnostic run: `SessionTimeout` 3 -> 4 and `OptInPolicy` false -> true are accepted (so the Put does write), but `RFBPassword` and `Is5900PortEnabled` are refused with `UnsupportedFeature` whatever OptInPolicy is (alone or together). Conclusion: on this device (AMT 14.1.79 at 192.168.10.69) the built-in VNC server on 5900 cannot be enabled; the KVM has to be reached through the redirection port 16994 (the Intel redirection protocol: StartRedirectionSession `KVMR`, digest authentication, then RFB 4.0), which needs a client of its own. SOL and IDER use the same port and the same authentication.

## Intel AMT redirection protocol on 16994 (1.7.x), seen on the AMT 14.1.79 device
- `StartRedirectionSession` = `10 00 00 00` + `KVMR`; reply `11 00 00 00 01 00 0e 01 57 01 00 00 00` (13 bytes, status 0, OEM length byte 0). Authentication query `13 00 00 00 00 00 00 00 00` -> `14 00 00 00 00 01 00 00 00` + `04` (only digest offered). First digest request (`13 00 00 00 04`, LE32 length, user, empty realm and nonce, uri `/RedirectionService`, empty cnonce/nc/response/qop) -> `14 01 00 00 04 <len>` + realm (`Digest:<hash>`), nonce, qop `auth`. Final request with all fields (nc `00000002`) -> `14 00 00 00 04 00 00 00 00`.
- After authentication the KVM channel is silent for at least 5 s: the client must send first.
- Sending `RFB 003.008\n` right after authentication made the device answer `41 00 00 00 00 00 00 01` (8 bytes); with the first 4 bytes read as a redirection message, 0x41 is the reply to the KVM start message (0x40).
- KVM start: client `40 00 00 00 00 00 00 00` -> device `41 00 00 00 00 00 00 00` followed by `RFB 004.000\n`. Client `RFB 003.008\n` -> `02 01 80` (security types: 1 = None, 0x80 = Intel's). After the redirection login, type 1 (None) is what the bridge selects.
- The device's ServerInit (`03 20 02 58` = 800x600): 16 bpp, depth 16, little-endian, true colour, max 31/63/31, shift 11/5/0 (RGB565), name `Intel(r) AMT KVM` (length 16). TigerVNC's SetPixelFormat (32 bpp) plus a 22-encoding SetEncodings made the device send `02` and reset the connection; so the bridge keeps the device on RGB565 + Raw and converts for the viewer.
- Screen content from the device at 192.168.10.69: every pixel black (800x600), updates after the first are a 1x1 rectangle every 10 s. Pointer events made the device close the connection about 2.3 s after the first screen; view-only stays up.
- Wake test (`BOBCAT_AMT_WAKE=1`, Shift key down/up at 2, 4, 6 s through the bridge, view-only viewer): the screen stayed black and the connection ended between the first key press (2.0 s) and the second (4.2 s), so key events also end the session, like pointer events; with no input it stays up for as long as it was watched (30 s+). The device reports the KVM service as `Enabled but Offline` (EnabledState 6) and a black 800x600 picture: likely no active video source for AMT to capture (AMT's KVM only sees the integrated graphics output; a discrete GPU, a headless machine or a display that is off give a black frame). Input being refused in that state is a guess, not verified.

## What MeshCommander's KVM client does (meshcommander 0.9.5-a, `public/default.htm`, CreateAmtRemoteDesktop)
- Redirection: after digest authentication it reads the device's 12-byte version, sends `RFB 003.008\n`, reads the security types, sends type 1 (None), reads the 4-byte result, sends the shared flag `1`, reads ServerInit.
- SetEncodings: `16` (Intel RLE, zlib), `0` (Raw; "with AMT we can't omit RAW"), `1092`, then `-223` (desktop size). Pixel format: the device's default RGB565 (16 bit); `bpp == 1` switches to RGB332 with `SetPixelFormat 8,8,0,1, max 7/7/3, shift 5/2/0`. Gray modes use 8-bit and 4-bit formats.
- Limit: `bpp * width * height > 9 216 000` is flagged "Display buffer too large" (disconnect code 50002); disconnect codes 50000/50001 around the handshake mean "needs RLE8 or an unsupported GPU" / "Intel AMT initiated".
- Tiles: updates are 64x64 tiles; Raw tiles (encoding 0) are `w*h*bpp` bytes; RLE tiles (16) start with a 32-bit length and a zlib-framed block (a persistent inflate stream); sub-encodings 0 raw, 1 solid, 2..16 packed palette, 128 run-length.
- After each complete frame it sends an incremental FramebufferUpdateRequest (`03 01 0000 0000 w h`) for the whole screen. Keys: `04 down 00 00 keysym(4)`; pointer: `05 buttons x(2) y(2)`; both standard RFB. KVM data channel/keep-alive: ClientCutText (`06 00 00 00 len`) with `\0KvmDataChannel\0` every 5 s; extension commands use `\0KvmExtCmd\0<cmd><val>`.
- The device's first compressed RLE chunk starts with a zlib header: `78 9c` + a raw-deflate stored block (`00 03 00 fc ff`) + the tile (`01 00 00` = solid, colour 0x0000). The rest of the stream is raw deflate. (MeshCommander's comment: "Process the ZLib header if this is the first block".)

## AMT IDE-R (1.9.1, ported from MeshCommander's CreateAmtRemoteIder)
- Messages: 8-byte header (command, 3 zero bytes, sequence number little endian) and data. The client sends 0x40 OPEN_SESSION (receive timeout 30000, transmit timeout 0, heartbeat 20000 ms as little-endian 16-bit, then the version 1 as 32-bit); the device answers 0x41 (30 bytes + a length-prefixed OEM string: major/minor at 8/9, firmware at 10/11, read buffer at 16, write buffer at 18 (little endian), protocol at 21 which must be 0, IANA number at 25); the client then sends 0x48 DisableEnableFeatures type 3 with `0x01 + 0x08` (on next boot), `0x10` (graceful) or `0x18` (now). The device sends 0x50 with a SCSI command (device flags byte at 14: bit 0x10 = CD/DVD, otherwise floppy; CDB at 16..28; feature register at 9 whose bit 0 means DMA) and the client answers with 0x54 DataToHost (a 26-byte header incl. length and device) in pieces of at most the read buffer, 0x51 CommandEndResponse (sense data), or 0x52 for the data of a write. 0x44 ping is answered with 0x45; 0x46 reset with 0x47; 0x53 data from host is acknowledged with a fixed 0x51.
- Sequence numbers are checked on every message from the device; a gap ends the session. CD/DVD sectors are 2048 bytes, floppy 512; the images must be a whole number of them. Writes are refused (read-only).
- Boot from it: AMT_BootSettingData `UseIDER=true` and `IDERBootDevice` 1 (CD/DVD) or 0 (floppy), no boot source; the session must already be open (MeshCommander starts it first, then runs the power action).

## AMT boot source control (1.9.0, from Intel's documentation, not yet checked on a device)
- Sequence: Put `AMT_BootSettingData` (BIOSSetup, UseSOL, UseIDER and the other writable properties, the whole instance rebuilt from a Get); `CIM_BootConfigSetting` (selector InstanceID `Intel(r) AMT: Boot Configuration 0`) `ChangeBootOrder` with a `CIM_BootSourceSetting` reference (InstanceID `Intel(r) AMT: Force Hard-drive Boot`, `Force PXE Boot`, `Force CD/DVD Boot` or `Force Diagnostic Boot`; no `Source` clears the order); `CIM_BootService` (Name `Intel(r) AMT Boot Service`) `SetBootConfigRole` with that configuration and Role 1 (IsNext); then a power action starts the machine (the override is used once).
- MeshCommander 0.9.5-a (`public/default.htm`) uses the same names: `ChangeBootOrder` / `SetBootConfigRole` and the sources `Force Hard-drive Boot`, `Force PXE Boot` and `Force CD/DVD Boot`.
- To check on the device: that the Put of the AMT_BootSettingData is accepted (the KVM one needed the whole instance, see above), that the ChangeBootOrder source names are right for this firmware, and whether the override really lasts for one boot.
